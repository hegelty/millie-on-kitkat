# 검증 결과와 알려진 제한 사항

검증일: 2026-10-07. 현재 패치 번들: **0.2.5 실험 버전**, 지원 앱: **2.1.0.0·2.4.0.0**.

## GitHub Pages 변경 이력 연동 (2026-10-07)

Manager 2.6.0의 번들 상세 화면은 등록된 소스 URL의 도메인에서 `/v5/patches/history`를 요청합니다. 기존 GitHub Raw 소스에서는 이 요청이 404를 반환하는 것을 확인했습니다. `CHANGELOG.md`를 추가하는 것만으로는 앱 안에 변경 이력이 표시되지 않습니다.

`docs/`에 최신 번들 정보와 버전별 변경 이력 API를 구성하고, 사용자 지정 도메인을 `millie.hegelty.me`로 지정했습니다. 로컬 HTTP 서버에서 실제 요청 경로 두 개가 JSON을 반환하는 것을 확인했습니다. 생성기의 버전·날짜 일치 검사, 중복 버전 거부, 오래된 출력 거부 및 상대 문서 링크 변환도 검사했습니다. 기존 0.2.5 번들 파일은 변경하지 않았습니다.

## 0.2.3: 카르타 G에서 확인한 EPUB 터치 지연 완화

Android 4.4.2/API 19 카르타 G 실기기에 설치된 APK가 제공한 0.2.2 파일과 동일함을 SHA-256으로 확인한 뒤, 입력 단계별 시각을 기록했습니다. 사용한 다운로드 뷰어는 1.5.7이며, APK에 포함된 기본 뷰어 1.0.45와는 별도로 로드되고 있었습니다.

- 수정 전 손을 뗀 시점부터 네이티브 탭 처리 함수까지 약 2.94~3.49초가 걸렸습니다. 첫 탭의 이후 페이지 전환 명령까지는 4ms였고, 물리 버튼도 전환 명령까지 4ms였습니다.
- 임시 입력창을 생성해 포커스를 주고 제거하는 함수가 터치 및 마우스 이벤트에서 두 번 실행됐습니다. 반복 측정에서는 각 호출이 약 835~892ms였고, 이벤트 사이에도 지연이 있었습니다.
- 이 함수만 생략한 실기기 시험에서 탭 7건의 손 떼기→네이티브 탭 처리 시간은 1,796/26/23/178/23/23/22ms였습니다. 첫 입력의 지연은 남았으므로 모든 탭이 즉시 처리된다고 주장하지 않습니다. 이 수치는 화면 갱신 완료까지의 시간이 아닙니다.
- 사용자는 터치가 물리 버튼과 비슷한 속도로 빨라졌으며, 글자 길게 누르기 선택과 해제도 정상이라고 확인했습니다. 특정 기기와 도서에서의 결과이며 모든 도서·링크·주석 기능을 검증한 것은 아닙니다.
- 정식 변환기는 기본 1.0.45 및 다운로드 1.5.7의 확인된 함수 본문만 제거합니다. Java 코드로 실제 라이브러리 두 종류를 변환해 변경 범위·중복 입력·미확인 코드·재적용·API 18/20/23/35 무변경을 검사했고, 변환 결과는 JavaScript 구문 검사를 통과했습니다.

- 2.1·2.4 코어 검사, 변조·손상 입력 및 미지원 2.5 거부 검사를 통과했습니다. 2.1의 패치 결과는 유지됩니다.
- CLI 6으로 원본 2.4 APK에 최종 번들을 적용했습니다. ZIP CRC, 변경 파일 범위, DEX 체크섬과 델타 대상 해시, 기존 업데이트 분기를 독립 검증했고, v1/v2/v3 서명도 통과했습니다. 진단용 클래스·JavaScript 수정은 최종 APK에 포함하지 않습니다.
- 반복 빌드에서 번들 SHA-256이 같았습니다. Manager에서 별도로 패치하는 검사는 아직 하지 않았습니다.

번들: `millie-eink-patches-0.2.3.rvp`, 7,503,828바이트, SHA-256 `17ca688fff1b2a9adaa9ab6790fff6decea3ffd6e383600878a650944c4812cd`. 내부 DEX3: `061a37336962409d781c608429cd738e99381b527b654310e839780e22eac80e`.

- 최종 CLI APK를 같은 서명으로 실기기에 덮어 설치했고, 설치된 APK의 SHA-256이 생성물과 일치했습니다. 임시 수정한 다운로드 뷰어 파일을 원본 해시로 복구한 상태에서 책장 및 EPUB 화면 진입을 확인했으며, 해당 앱 프로세스에서 치명적 예외는 관찰되지 않았습니다. 사용자는 최종 APK가 캐시 시험본보다 조금 느리지만 사용 가능한 수준이라고 보고했습니다. 두 빌드의 성능이 같다고 판단하지 않으며, 추가 차이의 원인은 아직 확인하지 못했습니다. 시험본의 진단 코드만 제거한 뷰어와 최종 Java 변환기의 출력은 바이트 단위로 일치했습니다.

## 0.2.2: 2.4 EPUB 터치 좌표 처리 최적화

물리 버튼보다 터치 반응이 느리다는 사용자 보고를 받아 2.4.0.0을 조사했습니다. 이번 보고에서 앱·패치 버전, 메뉴와 책장도 느린지 여부는 아직 확인하지 못했습니다. 앞선 대화의 2.4.0.0을 기준으로 조사했으며, 실제 카르타 G에서 입력 지연을 측정한 결과는 아닙니다.

**실기기 재시험 결과:** 사용자는 제공한 0.2.2 APK에서도 지연이 그대로라고 보고했습니다. 본문에서 탭과 스와이프가 모두 느리며, 터치로 메뉴를 연 뒤 메뉴를 조작할 때는 빠릅니다. 따라서 아래 좌표 처리 최적화가 실제 체감 지연을 해결했다고 판단하지 않습니다. WebView 입력부터 페이지 이동 요청까지 추가 진단이 필요합니다.

EPUB 터치 시작·종료·탭은 JavaScript 브리지를 거쳐 메인 스레드에서 `ContentEvent(String)`을 생성합니다. 이 생성자는 이벤트마다 Kotlin 모듈을 포함한 Jackson 변환기를 새로 만들고 있었습니다. 물리 버튼은 좌표 해석을 거치지 않고 페이지 이동을 요청합니다. 0.2.2는 이 생성자가 같은 설정의 변환기를 재사용하도록 수정하며, 터치 인식이나 페이지 이동 규칙은 바꾸지 않습니다.

- API 19 ARM 에뮬레이터에서 기존 생성자와 변환기 재사용을 비교했습니다. 첫 예비 측정에서 초기 로딩 이후 좌표 10건은 기존 방식 625~1,055ms, 재사용 방식 3~4ms였습니다. 이 숫자는 JSON 좌표 처리 구간만 측정한 결과이며, 실제 페이지 전환 속도나 카르타 G에서의 개선율을 뜻하지 않습니다.
- 수정한 내부 DEX를 사용하는 별도 진단 APK에서 같은 `ContentEvent(String)` 생성자를 측정했습니다. 좌표 10건은 기존 코드 331~791ms, 수정 코드 12~24ms였습니다. 정상·소수점·빈 객체·JSON null·Java null·null 좌표·문자열 숫자·문법 오류·정수 범위 초과의 9가지 입력에서 getter 결과가 수정 전후 일치했습니다. 진단 코드는 배포 번들에 포함하지 않습니다.
- 2.1·2.4 코어 검사, 잘못된 내부 DEX에 터치용 델타를 적용하는 경우의 거부 검사, 미지원 2.5 입력 거부 검사를 통과했습니다. 2.1 결과, 2.4의 외부 DEX·기존 내부 DEX 수정·네이티브 변경은 그대로 유지됩니다.
- CLI 6 출력은 독립 APK 내용 검증과 v1/v2/v3 서명 검증을 통과했습니다. 독립 조립 시험본과 새 내부 DEX 내용이 같습니다. JVM과 Python의 ZIP 포장 차이 때문에 `assets/classes.jet` 암호문은 다르지만, 그 외 서명 파일을 제외한 내용은 같습니다.
- 진단 코드가 없는 독립 조립 시험본을 같은 시험 키로 덮어 설치했고, 앱 데이터의 표식 파일이 유지됐습니다. 빈 도서 정보로 EPUB 초기화 후 40초, 앱 재실행 후 25초 관찰에서 치명적 예외가 없었습니다. 이는 실제 도서 읽기 검사가 아닙니다.
- 반복 빌드에서 번들 SHA-256이 같았습니다. 이 버전은 Manager에서 별도로 생성하는 검사를 아직 하지 않았습니다.

번들: `millie-eink-patches-0.2.2.rvp`, 4,860,589바이트, SHA-256 `e68fd700b0d127c950d4e487150400510bb4d7325e47712ff1d1ab35a2963540`.

실제 도서 읽기와 터치·길게 누르기·메뉴 조작은 실기기에서 추가 확인해야 합니다. 첫 JSON 변환기 생성 비용은 남아 있으며, 이번 수정이 앱 전체의 터치 지연을 해결한다고 단정하지 않습니다. 2.4는 계속 실험적 버전입니다.

## 0.2.1: 2.4 뷰어 초기화 오류 보완

사용자가 2.4에서 도서를 열 때 종료된다고 보고한 뒤, API 19 / ARMv7 에뮬레이터에서 EPUB 뷰어를 직접 실행해 추가 진단했습니다. 실제 계정이나 도서는 사용하지 않았으며, 도서 정보로 빈 JSON 객체를 전달했습니다.

- 0.2.0 APK에서는 `AssertionError: Built-in class kotlin.Any is not found`가 발생했습니다. APK에 Kotlin 메타데이터 파일은 존재했지만 별도 DEX 클래스 로더에서는 해당 리소스를 열 수 없었습니다.
- 진단용 수정에서는 동일한 클래스 로더의 리소스 검색 결과가 `false`에서 `true`로 바뀌었습니다. 정식 수정 코드에서도 `APK resources visible to packed classes` 로그와 EPUB 화면의 활성 상태를 확인했습니다.
- 별도 진단 코드로 EPUB의 `ContentEvent` 클래스에 Kotlin reflection의 `getMembers()`를 호출했습니다. 기존 코드에서는 `Built-in class kotlin.Any is not found`가 발생했고, 수정 코드에서는 멤버 10개를 반환했습니다. 이 검사는 실제 도서 정보 없이 메타데이터 로딩 오류를 직접 재현합니다. 진단 코드는 배포 번들에 포함하지 않습니다.
- 기존 종료 오류를 재현한 EPUB 초기화 검사를 수정 후 반복했으며, 40초 관찰 중 해당 오류나 치명적 예외는 없었습니다. 빈 도서 정보로 실행한 PDF 뷰어 검사에서도 치명적 예외는 없었습니다. 이는 도서 본문을 실제로 읽은 검사가 아닙니다.
- 2.1·2.4 코어 검사를 통과했습니다. Kotlin 메타데이터 일곱 개도 원본 해시 검사에 추가했습니다. 2.1의 기준 결과와 2.4의 내부 DEX 수정 결과는 유지됩니다.
- CLI 결과는 독립 APK 내용 검증과 v1/v2/v3 서명 검증을 통과했습니다. 독립적으로 조립한 수정 시험본과 `META-INF/` 외 파일 내용이 모두 같습니다.
- Manager 2.6.0에서도 0.2.1을 가져와 APK 생성·서명·내보내기를 확인했습니다. 독립 검증과 v1/v2/v3 서명 검증을 통과했고, CLI 결과와 `META-INF/` 외 1,080개 파일 내용이 모두 같습니다. 재빌드한 번들의 SHA-256도 같았습니다.
- 같은 시험 서명 키로 만든 CLI 0.2.0 결과에 0.2.1 결과를 `adb install -r`로 덮어 설치했습니다. 앱 데이터 디렉터리의 시험용 표식 파일이 유지됐고, 이후 로그인 화면 진입, EPUB 초기화 65초 관찰, 다시 로그인 화면으로 재실행하는 검사에 치명적 예외가 없었습니다. 실제 계정·다운로드 도서가 남아 있는 상태의 검사는 아닙니다.

빈 도서 정보만 전달한 새 설치 시험에서는 0.2.0의 종료가 재현되지 않은 경우도 있었습니다. 따라서 도서 없는 초기화 검사만으로 사용자 기기의 반복 종료 조건 전체를 재현했다고 판단하지 않습니다.

## 알려진 문제

사용자는 크레마 카르타 G에서 2.4.0.0 패치본으로 **책을 열자마자 종료되며, 이후 재실행할 때도 즉시 종료된다**고 보고했습니다. 실기기 종료 로그는 아직 확보하지 못했습니다. 별도 에뮬레이터 진단에서는 EPUB 초기화 중 Kotlin 리소스 검색 오류를 재현했고, 0.2.1에서 해당 오류를 보완했습니다. 실기기 보고와 원인이 같은지는 재확인이 필요합니다. 앞선 에뮬레이터 결과는 로그인 화면까지의 검사이며 독서 기능의 정상 동작을 뜻하지 않습니다. 원인이 해결될 때까지 2.4.0.0을 실사용 가능한 버전으로 판단하면 안 됩니다.

Manager의 첫 생성 결과에서 수정 대상이 아닌 PDF 라이브러리의 압축 데이터가 손상돼 ZIP CRC 검사가 실패했습니다. 같은 원본과 같은 번들로 다시 생성한 결과는 CRC·파일 내용·서명 검증을 모두 통과했지만, 첫 손상의 원인은 확인되지 않았습니다.

따라서 아직 모든 기기에서 안정성을 확인한 버전은 아닙니다. 패치 결과에 설치 오류나 실행 이상이 있으면 해당 파일을 계속 사용하지 말고, 원본 버전과 패치 선택을 확인한 뒤 다시 생성하세요. 개발자는 [검증 도구](README.md)로 출력 파일을 확인할 수 있습니다. 서명 검증만으로 파일 내용의 정상 여부를 판단할 수는 없습니다.

0.2.0에서 2.4.0.0을 추가했으며, 기존 2.1.0.0도 계속 지원합니다. 다른 패치와의 조합과 후속 Manager 버전은 검증하지 않았습니다. ABI별 제한과 상위 앱 버전의 별도 시험 결과는 아래에 기재했습니다.

추가 비교에서는 다음과 같은 제한을 확인했습니다.

- **Android 9·10 / x86_64:** 원본과 패치본이 모두 종료됐습니다. 패치본에서는 해당 ABI용 Conscrypt JNI가 없다는 로그도 확인했습니다. 원본도 종료되므로 OS 버전이나 패치만의 문제로 판정할 수 없습니다.
- **Android 11 / ARM64 변환 실행:** 원본과 패치본이 모두 종료됐습니다. 같은 시스템 이미지에서 ARM32 패치본은 실행됐습니다. ARM64 결과는 ARM64 실기기 검증을 대신하지 않습니다.
- **Android 10 / ARM64:** 현재 호스트에서 ARM64 시스템 이미지를 실행할 수 없어 검사하지 못했습니다.
- **Android 13 / ARM32:** 시험 이미지가 ARM32를 지원하지 않아 검사하지 못했습니다. 앱의 호환성 실패로 계산하지 않습니다.

현재 패치는 **ARM32(ARMv7)만 보완**합니다. 원본 APK에 들어 있는 ARM64·x86·x86_64 모듈에는 변경된 DEX에 맞춘 무결성 정보와 실행 호환성 수정이 적용되지 않습니다. 따라서 Android 버전만으로 지원 여부를 판단하면 안 됩니다. 이번 결과에서 Android 버전 상승에 따른 일률적인 실행 중단 경계는 확인하지 못했습니다.
